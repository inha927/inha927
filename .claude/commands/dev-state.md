# 상태 아카이브

목표는 하나다 — **다음 세션(어느 AI든)이 파일 하나에서 시작해 바로 이어서 작업할 수 있게 한다.**

## 0. 먼저 프로젝트 형태를 판별한다

| 형태 | 판별 | 갱신 대상 |
|---|---|---|
| **A. 정본형** | 루트에 `AGENTS.md` + `Docs/` 폴더 | 그 체계의 문서 (아래 A절) |
| **B. 단일형** | 루트에 `DEV_STATE.md` | `DEV_STATE.md` (아래 B절) |
| **C. 없음** | 둘 다 없음 | `DEV_STATE.md` 새로 만든다 (B절 구조로) |

**A인데 DEV_STATE.md를 새로 만들면 안 된다. 정본이 둘이 되면 체계가 죽는다.**

## A. 정본형 (예: 플라이 이스케이프 UEFN 프로젝트)

1. `AGENTS.md`의 작업 규칙을 먼저 읽고 따른다 (문서 소유권·자기 점검 절차 포함)
2. `Docs/AI 작업 잠금/`에 `status: "ACTIVE"`가 있으면 그 파일은 건드리지 않는다
3. 갱신 위치는 체계의 소유권을 따른다:
   - 진행 상황·다음 할 일 → **인수인계 문서**에 날짜 절(§) 추가. 기존 절은 지우지 않는다
   - 실기 PASS/FAIL → **테스트 기록.md**에만. **실행 안 한 검증은 어디에도 PASS로 적지 않는다**
   - 수치·게이트 → 실행 스펙 (게임 규칙 변경은 사용자 승인 필요)
4. git 커밋하지 않는다 — 이 형태는 UEFN Revision Control이 동기화를 담당한다

## B. 단일형 — DEV_STATE.md

### 확인 순서 (추측 금지)

```
1. git status / git diff / git log --oneline -20
2. 기존 DEV_STATE.md — 단, 코드와 어긋나면 코드가 정답이다
3. 테스트·빌드 결과 — 돌려본 것만. 안 돌렸으면 "미실행"
```

### 구조

```markdown
# DEV_STATE
> 갱신: YYYY-MM-DD · 브랜치: <branch>
## 지금 목표
## 완료된 것          (검증 방법까지)
## 핵심 결정과 이유    (왜 — 이게 제일 가치 있다)
## 핵심 파일          (경로 + 한 줄 역할)
## 테스트·검증 상태    (통과/실패/미실행)
## 알려진 문제
## 실패한 접근        (같은 벽에 다시 부딪히지 않게)
## 다음 할 일
```

### 규칙

- 확인된 사실만. 불확실하면 `[추정]` / `[미확인]` 표시
- 코드 붙여넣기 금지 (경로와 역할만) · **민감정보(비밀번호·토큰·키·쿠키) 절대 금지**
- 해결된 이슈·폐기된 논의·중복은 삭제한다. 분량은 **한 화면**
- git 저장소면 상태 파일 변경만 커밋하고 푸시한다 (다른 기기·클라우드 세션이 읽도록)

## 마지막

무엇을 추가·삭제·수정했는지 3줄로 보고한다.
