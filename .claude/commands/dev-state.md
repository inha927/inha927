# DEV_STATE 갱신

프로젝트 루트의 `DEV_STATE.md`를 **실제 상태 기준으로** 새로 쓴다.
이 파일 하나만 읽으면 다음 세션이 바로 이어서 작업할 수 있어야 한다.

## 1. 먼저 확인한다 (추측 금지)

이 순서대로 **실제로 확인**한다. 안 본 것은 쓰지 않는다.

```
1. git status / git diff / git log --oneline -20   → 지금 뭐가 바뀌었나
2. 기존 DEV_STATE.md                                → 이전 스냅샷
3. 코드·설정 파일                                    → 문서와 실제가 다르면 실제가 맞다
4. 테스트·빌드 결과                                  → 돌려본 것만. 안 돌렸으면 "미실행"
```

**기존 DEV_STATE.md의 내용을 그대로 믿지 마라.** 코드와 어긋나면 코드가 정답이다.

## 2. 이 구조로 쓴다

```markdown
# DEV_STATE

> 갱신: YYYY-MM-DD · 브랜치: <branch>

## 지금 목표
## 완료된 것          (검증 방법까지)
## 핵심 결정과 이유    (왜 이 방식인가 — 이게 제일 중요하다)
## 핵심 파일          (경로 + 한 줄 역할)
## 테스트·검증 상태    (통과/실패/미실행)
## 알려진 문제
## 실패한 접근        (다시 시도하지 않기 위해)
## 다음 할 일
```

## 3. 규칙

**쓸 것**
- 확인된 사실만. 불확실하면 `[추정]` / `[미확인]`으로 표시
- **왜 그렇게 했는지.** 무엇을 했는지보다 이게 더 가치 있다
- **실패한 접근과 그 이유.** 다음 세션이 같은 벽에 다시 부딪히지 않게

**쓰지 말 것**
- 코드 붙여넣기 (경로와 역할만)
- 비밀번호·토큰·API 키·개인키·쿠키 등 민감정보 — 절대
- 끝난 논의, 폐기된 아이디어, 중복 내용
- "적절히", "대략" 같은 말. 수치는 수치로

**삭제할 것**
- 이미 해결된 이슈, 더 이상 유효하지 않은 계획, 옛 파일 경로

## 4. 분량

**한 화면.** 길어지면 압축이 아니다. 세부는 별도 문서로 빼고 여기서는 링크만 건다.

작성 후 무엇을 추가·삭제했는지 3줄로 보고한다.
